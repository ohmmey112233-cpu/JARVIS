# สถาปัตยกรรม — ทำไมโค้ดถึงแบ่งแบบนี้

## การตัดสินใจข้อเดียวที่สำคัญที่สุด: แยกแกนออกจาก Hermes

```
┌─────────────────────────────────────────────────────────────┐
│  Hermes Agent  (อาจถูกเปลี่ยนทิ้งได้ถ้า gate trial ไม่ผ่าน)      │
│  ┌───────────────────────────────────────────────────────┐  │
│  │  skills/jarvis-*/SKILL.md                             │  │
│  │  บอก agent ว่า "เมื่อไหร่ควรเรียก" และ "ตอบยังไง"          │  │
│  │  ── ไม่มีตรรกะทางธุรกิจอยู่ในนี้เลย ──                     │  │
│  └────────────────────────┬──────────────────────────────┘  │
└───────────────────────────┼─────────────────────────────────┘
                            │  เรียกผ่านคำสั่งเชลล์ คืน JSON
                  ┌─────────▼──────────┐
                  │   jarvis/cli.py    │  สะพานบางๆ แปลง argv → เรียกฟังก์ชัน
                  └─────────┬──────────┘
┌───────────────────────────▼─────────────────────────────────┐
│  jarvis/core/   ← ของจริงอยู่ตรงนี้ทั้งหมด                       │
│                                                              │
│  localdate  friday  routines  memory  digest  booking        │
│  webhook    scaccounting    db                               │
│                                                              │
│  Python ล้วน + stdlib + sqlite3 เท่านั้น                       │
│  ไม่รู้จัก Hermes / ไม่เรียก LLM / ไม่ต่อเน็ต                    │
└───────────────────────────┬─────────────────────────────────┘
                  ┌─────────▼──────────┐
                  │    jarvis.db       │  SQLite
                  └────────────────────┘
```

### เหตุผล

spec v3 เขียนไว้ตรงๆ ว่า:

> *"ผ่านครบ → Track A (Hermes) / ไม่ผ่านข้อไหน → Track B (สร้างเองตาม spec v2)
> — **งาน Phase 1-5 ข้างล่างเหมือนกันทั้งสอง track ต่างแค่ฐาน**"*

ถ้าเขียนตรรกะทั้งหมดเป็น Hermes skill แล้ว gate trial ไม่ผ่าน = เขียนใหม่หมด
แบ่งแบบนี้แล้ว **ถ้าต้องไป Track B ทิ้งแค่ `skills/` กับ `cli.py`** ซึ่งรวมกันไม่ถึง 10%
ของโค้ดทั้งหมด ส่วน `core/` ยกไปใช้กับฐานใหม่ได้ทันทีโดยไม่ต้องแก้อะไรเลย

ต้นทุนของการแบ่ง: ต้องเขียน `cli.py` เพิ่มมาหนึ่งไฟล์ — คุ้มกว่าความเสี่ยงที่จะเขียนใหม่ทั้งหมด

### กฎที่ทำให้การแบ่งนี้ไม่พังตามเวลา

| กฎ | บังคับด้วยอะไร |
|---|---|
| `core/` ห้าม import อะไรที่เกี่ยวกับ Hermes | เทสต์รันได้โดยไม่ต้องติดตั้ง Hermes |
| `core/` ห้ามเรียก LLM | เทสต์รันได้โดยไม่ต้องมี API key |
| `skills/` ห้ามมีตรรกะทางธุรกิจ | SKILL.md เป็น markdown ล้วน เขียนตรรกะไม่ได้อยู่แล้ว |
| ตรรกะใหม่ทุกอย่างลง `core/` | มีเทสต์คู่ทุกโมดูล |

## กฎเหล็ก 3 ข้อจาก spec — บังคับตรงไหนในโค้ด

### 1. คำสั่งบ้านง่ายๆ ห้ามผ่าน LLM

ยังไม่มีผลใน Phase 1 (ยังไม่มี Home Assistant) แต่โครงรองรับไว้แล้ว:
คำสั่งบ้านจะไม่ผ่าน `core/` เลย ไปที่ HA automation ตรงๆ
(red-team H8/H9 — ต้องทำงานได้แม้เน็ตล่ม และไม่ต้องรอ 5 วินาที)

### 2. เปิด dashboard ห้ามเรียก AI

Phase 6 ยังไม่ถึง แต่ `core/` เป็น deterministic ล้วนอยู่แล้ว
dashboard อ่านจาก `core/` ได้โดยไม่มีทางเผลอเรียก LLM

### 3. ทุกที่ที่ถามว่า "วันนี้วันไหน" ใช้ Asia/Bangkok

บังคับที่ `core/localdate.py` — โมดูลอื่นห้ามเรียก `datetime.now()` เอง
ทุกฟังก์ชันที่เกี่ยวกับเวลารับ `clock=None` เพื่อให้เทสต์ฉีดเวลาเข้าไปได้

**ทำไมข้อนี้ถึงต้องเข้มขนาดนี้:** เที่ยงคืน UTC = 07:00 เช้าไทย
ถ้าพลาด routine จะรีเซ็ตตอน 7 โมง คือ *หลัง* digest เช้าส่งไปแล้วพอดี
ข้อมูลจะเพี้ยนทุกวันโดยไม่มีอะไรฟ้อง — เป็นบั๊กที่กว่าจะรู้ตัวก็ผ่านไปเป็นเดือน

## ไหลของข้อมูลตอน digest เช้า

```
06:20  Hermes cron ยิง (timezone Asia/Bangkok)
   │
   ├─→ cli routines due        ─→ core.routines  ─→ jarvis.db
   ├─→ cli friday state        ─→ core.friday    ─→ jarvis.db (friday_anchor_date)
   ├─→ Google Routes API        ─┐
   ├─→ Longdo Weather API       ─┤  API ตัวไหนล่ม = ข้ามหัวข้อนั้น
   ├─→ Air4Thai API             ─┤  ไม่ใช่ทั้ง digest หายไป
   ├─→ Google Calendar API      ─┘  (checklist E2)
   │
   └─→ core.digest.render_morning(ctx)   ← ประกอบข้อความ deterministic
           │                                ไม่เรียก LLM ตรงนี้
           └─→ Telegram (Phase 1) / LINE (Phase 2)
                   └─→ บันทึกลง notifications_sent (นับโควตา H14)
```

`core.digest` ไม่ไปดึงข้อมูลเอง — รับ `DigestContext` ที่ประกอบมาแล้ว
แยกแบบนี้ทำให้เทสต์ทุกรูปแบบข้อความได้โดยไม่ต้องมีเน็ตหรือ API key สักตัว

## ตารางในฐานข้อมูล

| ตาราง | ที่มา | ใช้ทำอะไร |
|---|---|---|
| `routines` | phase1-kit §3 | ไดโอด/คิ้ว/ตัดผม |
| `preferences` | phase1-kit §3 | ค่าคงที่ แก้ได้โดยไม่แก้โค้ด |
| `class_schedule` | phase1-kit §3 | ตารางเรียน ให้ digest บอกคาบแรก |
| `lessons` + `lessons_trash` | phase1-kit §5 + H13 | ความจำ + ถังขยะกู้คืนได้ |
| `bookings` | อนุมาน (ไม่มี spec v2) | คำขอจอง + ซองคำตอบล่วงหน้า |
| `call_logs` | อนุมาน (ไม่มี spec v2) | บันทึกสาย + latency ตาม H5 |
| `notifications_sent` | อนุมาน + H14 | นับโควตา LINE 300/เดือน |

⚠️ สามตารางที่เขียนว่า "อนุมาน" — spec v3 บอกว่า *"ตารางตาม spec v2"* แต่ไม่มีไฟล์ v2
ให้ดู คอลัมน์จึงอนุมานจากบริบทที่ spec v3 กับ red-team บรรยายไว้
**ถ้าหาไฟล์ spec v2 เจอ ให้เทียบก่อนใช้จริง** — ทำเครื่องหมายไว้ในไฟล์ SQL แล้ว

## สิ่งที่ยัง "ไม่" ได้ทำในโค้ดชุดนี้

ระบุไว้ให้ชัดเพื่อไม่ให้เข้าใจผิดว่าพร้อมกว่าที่เป็นจริง

| ส่วน | สถานะ |
|---|---|
| โทรจองจริง (Twilio/Vapi/Botnoi) | ❌ `booking.py` บันทึกคำขอได้ แต่ยังโทรไม่ได้ — Phase 3 |
| ประกอบ+ส่ง digest | ✅ `assemble.py` + `cli digest` + cron `--no-agent` — deterministic ทั้งเส้น ไม่ผ่าน LLM |
| ต่อระบบบัญชีจริง | ❌ ด่านความปลอดภัยพร้อม แต่ยังไม่มี transport — Phase 2 (ต้องมี OAuth ก่อน) |
| API เสริม digest (Weather/AQI) | ⚠️ `core/fetchers.py` เขียนแล้วแบบฉีด transport ได้ — **ตัวแปลง response ยังไม่เคยเจอ API จริง** ต้องตรวจ shape ตอนต่อจริงบน VPS |
| เวลาเดินทาง หอ→โรงเรียน | ❌ **ตัดออกโดยตั้งใจ** — เดิน 2 นาที (วัดจริง) ไม่มีอะไรให้ตัดสินใจ ระบบข้ามการยิง API เองเมื่อระยะ <1 กม. และจะกลับมาทำงานเองถ้าย้ายหอ |
| LINE gateway | ❌ Phase 2 |
| Home Assistant | ❌ Phase 5 (มีเงื่อนไข H6/H7 ต้องเคลียร์ก่อน) |
| Sushiro | ❌ Phase 4 — แต่ `friday.is_in_chiang_mai_on_friday()` พร้อมให้เรียกแล้ว (H10) |
